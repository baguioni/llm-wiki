# Open Questions

* [Does offloading the KV cache to CPU memory help agentic workloads?](kv-cache-offloading-for-agent-workloads.md) - Agent-serving papers disagree on whether moving idle KV cache off the GPU during tool calls improves throughput.
* [Does speculative decoding still help at large batch sizes?](speculative-decoding-at-large-batch.md) - Papers disagree on whether speculative decoding keeps a speedup above 1 when the server batches many requests.
* [How can a mobile-efficient drafter be built cheaply for a new target?](cost-efficient-drafter-construction.md) - Given an arbitrary target LLM with no suitable first-party or size-matched drafter, how can a drafter that fits a phone NPU be constructed at low training cost; the papers measure construction cost for server drafters only.
* [How large are the standard drafter training sets?](drafter-training-set-sizes.md) - EAGLE-3, SpecForge, and DSpark give different sizes for ShareGPT, UltraChat, and Open-PerfectBlend, in different units and without versions or filtering steps, so the data budgets of published drafters cannot be compared exactly.
* [How much acceptance does quantizing the draft or the target cost?](quantization-and-acceptance.md) - No source in the wiki varies only the bit width (4-bit, 8-bit, 16-bit) of the draft or the target and measures acceptance and speedup; the comparisons that exist also change placement, budget, vocabulary, or activation format.
* [Is Deep Memory Retrieval an adequate benchmark for agent memory?](deep-memory-retrieval-adequacy.md) - MemGPT presents Deep Memory Retrieval as evidence that a memory system is needed, while Zep shows a full-conversation baseline that matches it.
* [Should agent training environments verify tasks with code or with an LLM judge?](code-verification-vs-llm-judge.md) - VeriEnv argues for deterministic code validators and Agent World Model argues that code-only verification is brittle.
* [Was PARD-2's Qwen3-14B drafter trained to run without target features?](pard-2-qwen3-14b-feature-gating.md) - PARD-2's hyperparameter table gives a stochastic gating ratio of 0.0 for Qwen3-14B while its implementation details give 0.1, so it is unclear whether its Qwen3-14B drafter ever trained without target features and whether it can run feature-free.
* [What is the GSM8K score of Sheared-LLaMA 2.7B?](sheared-llama-gsm8k-discrepancy.md) - Two papers report GSM8K scores for Sheared-LLaMA 2.7B that differ widely (2.7 and 23.96).
* [Which SWE-bench Verified scores are comparable?](swe-bench-verified-comparability.md) - Papers quote the same systems on SWE-bench Verified with different scores and different rollout budgets.
* [Why do reported EAGLE-3 numbers differ so much between papers?](eagle-3-baseline-variance.md) - EAGLE-3 speedup and acceptance length for the same target model differ widely across the papers that re-measure it.
* [Does speculative decoding help on a mobile NPU?](speculative-decoding-on-mobile-npu.md) - Lever measures speculative decoding with NPU verification on Snapdragon phones, but only for a target streamed from flash and with no energy numbers, so the case of a DRAM-resident target and its energy cost stays open.
* [Does starting a block drafter from the target's own layers cut its training cost?](target-layer-initialization-for-block-drafters.md) - DFlash-style drafters share the target's embedding and head but train their layers from scratch, and no paper tests starting those layers from target layers.
* [Does an acceptance-oriented loss help a block diffusion drafter?](acceptance-oriented-loss-for-block-drafters.md) - LK losses raise acceptance for autoregressive and MTP drafters, but no paper isolates their effect on a block diffusion drafter, and the gains at temperature 0 are small.
* [Can a block drafter pre-draft with stale target features?](pre-drafting-with-stale-target-features.md) - In mobile-server speculative decoding the phone idles while the server verifies, but a DFlash-style drafter needs target features that arrive only with the verify response.
* [What is the smallest block drafter that keeps acceptance with a sequential head?](minimum-drafter-depth-with-sequential-head.md) - A 2-layer DSpark beats a 5-layer DFlash on Qwen3-4B on server GPUs, which suggests a much smaller phone drafter; on my phone the 5-layer DSpark's Markov head costs 8.48-23.68 ms per round on the host CPU and cancels its acceptance gain, while on the server GPU it costs 3.0 ms as a chain, and the head has not been tried on the NPU.
* [Learned policy or calibrated confidence for choosing the verify set?](learned-vs-confidence-scheduled-verification.md) - Learning to Draft picks tree depth and verification size with RL policies and DSpark picks chain prefixes with calibrated confidence and a profiled throughput curve, but no paper compares the two or tests either on the other's drafter.
* [Can a block drafter be narrower than its target?](narrow-block-drafter.md) - DFlash and DSpark drafters run at the target's hidden size because they share its frozen embedding and LM head, which makes them expensive on a phone NPU, and no paper tests a narrower drafter body or how it trains.
* [Why do tree-verified outputs diverge from chain outputs at temperature 0?](fp8-verifier-tree-output-divergence.md) - In my drafter evaluation, tree arms reproduce the chain arms' greedy output on only 28-33 of 60 requests; the report attributes this to FP8 verifier numerics that change with the number of verified rows, but a tree-verify bug has not been ruled out.
* [Can a pruned target be turned into a parallel drafter?](pruned-target-to-parallel-drafter.md) - PARD converts a small same-series autoregressive model into a parallel drafter and Minitron-style pruning can produce such a model from the target; no paper chains the two, my first run of the chain on Qwen3-14B reaches offline MAT 1.96 at K=8 against 2.66 for a same-recipe Qwen3-0.6B drafter, and DFlash and PARD-2 disagree on how far a PARD drafter can go.
* [Does proactive drafting help when the drafter runs on a phone?](proactive-drafting-on-a-phone.md) - SpecEdge reports that proactive edge drafting lowers inter token latency on RTX 4090 edges, while HyCo finds that it lowers delivery speed on a phone NPU even as it raises server saving.
* [Does recovering a pruned drafter against the target beat recovering it against its parent?](target-aware-recovery-of-pruned-drafters.md) - Pruned drafters in the wiki are recovered against their own unpruned parent, a generic language-modeling objective, or not at all; only HAT trains against the target, and only a small adapter, so no paper measures whether target-aware recovery raises acceptance over self-recovery; my Qwen3-14B run recovers a pruned target against itself with one loss only.
* [Does choosing what to prune by target agreement beat LM-loss importance?](target-agreement-pruning-criteria.md) - Pruned drafters in the wiki choose what to remove by LM-loss or perplexity change, a Fisher trace on WikiText2, an unstated Bayesian-optimization objective, or layer position, and none scores candidate removals by acceptance or TV distance to the target; Minitron's candidate rankings shift during retraining, so it is also open whether any prune-time score predicts acceptance after recovery.
* [Do PARD-2's CAT and KD losses help a drafter trained without target features?](feature-free-pard-2-losses.md) - PARD-2's confidence-adaptive weighting and distillation term need only target probabilities, not hidden states, but every PARD-2 ablation adds them on top of target features, so their effect on a drafter trained fully feature-free (PARD-1 architecture) is untested.
* [How fast can the server-only baseline go?](server-only-baseline-implementation.md) - The same Qwen3-0.6B chain7 draft runs server-only at 17.0 tok/s with specedge's server_only.py and 20.4 tok/s with my later PyTorch chain code, and the later runs still leave most draft paths unoptimized, so the phone-versus-server comparison rests on a baseline whose ceiling is unknown.
* [Which divergence should a draft model be distilled with?](drafter-distillation-divergence.md) - GKD and DistillSpec find the best divergence task-dependent and get good drafts from TVD and reverse KL, while AdaSPEC gets acceptance rates of 9-30% with TVD and reverse KL against 60% with forward KL, and LK Losses explains why pure TVD fails from random initialization.
